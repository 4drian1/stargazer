# qfq阻断：已找到本地解密路径

本机已装pytdx的GbbqReader可解析当前gbbq。文件5,828,656字节，开头记录数200,988，与4+29×记录数完全吻合；头/中/尾各64条共192条解密抽样均有合法日期和6位代码。原文件SHA未变。EVIDENCE.json与probe.py可复核。

原先“扫描不到标准日期，所以本地不可解析”结论应更正：扫描的是密文，不是解密后的29字节结构。旧失败报告保留，本证据追加；本轮没有全量解码，没有生成或验收qfq，更没有修改日线生产入口。

后续执行顺序：

1. GbbqReader().get_df(本机gbbq路径)全量解码；保留源SHA/读前后文件版本、解码器版本及SHA，原始记录只读。不要依赖猜测的gbbq.map偏移。
2. 以market+code识别证券，分类校验日期、公司行为类型、数值单位和重复/冲突；不同类型不能混用同一列含义。除权除息、股本变动及扩缩股分别处理，不把所有事件当分红。
3. 先固定qfq基准日P，仅使用到P已生效且允许使用的真实事件，与原始日线构建独立复权视图。历史回放逐个截止生成，不能引入未来公司行为；实际最早可知时间仍须另证。
4. 从解码结果挑跨真实除权日的样本，用通达信前复权显示/官方前复权接口对照，再与同截止、同基准的旧stockdb视图比。还要覆盖送转、配股等实际存在的类型；不能只选价格比率为1的平静窗口。
5. 价格、前收、ATR、选股特征和黄金端点分别核对；成交量/成交额不因为价格复权就随意同比缩放。实际执行价地图与复权计算基准的转换必须明确。
6. 通过后才能解除pending_gbbq并接入选股。历史股本事件另做时间序列验证，可用于处理base.dbf单日快照局限，但不能仅因解出事件就宣称全历史已覆盖。

若该版本最终有不支持的个别事件，使用通达信官方TQ日线dividend_type='front'或none时返回的ForwardFactor作另一来源/核验路径，先检查客户端支持和有效返回，不新增未授权网络批采或费用。保持raw/qfq分开，缺失不造因子，旧数据不覆盖，仍停在打包前。
