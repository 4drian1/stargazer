# R0-V1 复权覆盖补证：源端能力与验收规则（DRAFT 规格）

> 目的：明确"源端究竟能提供哪些完整性证据"，再据以制定验收规则。
> 依据：`data_source_provenance.py`（CANONICAL = stockdb HTTP `127.0.0.1:7899`，free-stockdb v0.3.2；
> 本地 `data_daily_parts` 为其**衍生品**，非取数源）、`adjustment_chain.py`（`factor_at` 仅乘入 `events` 列表内 `effective_date<=asof` 的事件）。
> 结论：缓存刷新、请求成功、因子可算，**都不能自动证明没有遗漏事件**。

## 1. 源端实际能提供什么
- **公司行为事件列表 `events`**：每码 `(date, mult)` 列表，来自 stockdb `复权` 表（`get_adjustment_http`）。这是当前复权链的唯一输入。
- **状态 `status`**：OK / EMPTY / MISSING（最终缓存）。刷新只更新状态或内容。
- **因子可算**：`factor_at(asof)` 仅基于 `events` 内事件连乘；事件缺失则因子静默错误。

## 2. 源端不能提供什么（关键）
- **不能自证完备性**：`events` 来自同一源，源本身是否返回了**完整**公司行为历史，无法由源自己证明。漏一次除权 → `factor_at` 偏差 → 伪尾部风险（用户已重点指出）。
- **不能自证尺度**：`data_daily_parts`（OHLC）为衍生品，RAW 或 QFQ 取决于上游构建对 stockdb `日k` 的查询方式；与 `events` 同源不同表，需独立核验（见窗口级尺度核销）。

## 3. 验收规则（coverage_verified 置 True 的必要条件，当前为**必要非充分**）
> **充分性说明（2026-10-13 收紧，暂不称充分条件）**：以下规则是覆盖完整性核验的**必要检查**，但**不能自动构成充分条件**。即便 R1–R4 全过，仍须记录每项检查的**来源、覆盖范围与完整性依据**，方可主张"已核验"；任何一项的裁定基准自身有盲区时，结论须相应降级为"在已知来源范围内未检出遗漏"。

候选 `(code, [P, W_end])` 须全部通过：
- **R1 独立台账交叉核验（重要核验路径，但非"唯一完整性基准"）**：以**独立公司行为台账**为重要交叉核验路径，用于发现缓存 `events` 的遗漏。但须先**评估台账自身的来源、覆盖范围与遗漏风险**：(a) 数据来源（交易所公告 / 分红送转专用源，须与 stockdb 不同源）；(b) 覆盖范围（哪些年份/板块/事件类型，是否亦有盲区）；(c) 遗漏风险（自身是否可能漏登某些事件类型/时段）。**在台账来源/覆盖/遗漏风险未充分评估、证据不足时，保持 `UNVERIFIED`，不得因"有独立台账"即宣称完整**。列出 `[P, W_end]` 内应含事件；任一在台账中但不在缓存 `events` 的事件 → 覆盖 **INCOMPLETE**。若台账自身来源/覆盖/完整性依据缺失或自身盲区未明，R1 不成立、结论降级为"在已知来源范围内未检出遗漏"。
- **R2 因子不连续即缺口（仅内部一致性，非完整性证明）**：对 `factor_at` 逐日差分，`>1` 的跳变（除权）必须能在 `events` 中找到对应 `date`；无对应日期的跳变 → 缺失事件 → INCOMPLETE。**注意**：R2 的数据仍来自**同一事件链**（`events` → `factor_at`），因此 R2 仅能检查 `events` 链**内部一致性**，**不能发现 events 与台账共同遗漏的事件**；R2 通过**绝不**可替代 R1，也**不得**被表述为完整性证明。
- **R3 刷新不创造事件**：缓存刷新仅补状态/内容；不能因"刷新成功"推定完备；R1/R2 仍须重跑。
- **R4 窗口端点受源快照约束**：若 `W_end` 超出源端当前同步最大日期，该窗口无法由当前源快照完整覆盖 → INCOMPLETE，直至源快照延展并复验。

`coverage_verified = True` 当且仅当 R1–R4 全部通过**且每项均登记来源/覆盖/完整性依据**；否则 `UNVERIFIED`（当前全 1,013 为 UNVERIFIED）。
